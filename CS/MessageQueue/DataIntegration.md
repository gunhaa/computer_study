# Part2. Data Integration

> Data integration means "making all the data an organization has available in all its services and systems."

- Part 1이 이론(로그란 무엇인가)이었다면, Part 2는 조직 문제이다
- 실제로 LinkedIn에서 겪은 고통과 그 해법이 담긴, 이 글에서 가장 실무적이고 가장 많이 인용되는 부분이다
- 모든 것에 우선해, 가장 중요한 것은 신뢰 가능한 데이터가 흐르는 데이터 파이프라인의 구축이 가장 중요하다

## 과거와 다른 데이터 구조

- 이벤트 데이터의 폭발
  - 전통적으로 DB에 저장되던 것은 "비즈니스 엔티티의 현재 상태"(사용자, 주문, 상품)였지만, 현재는 그것에 더해 "일어난 일" 자체가 데이터가 된다
    - 사용자 활동 로그(클릭, 노출, 스크롤, 검색)
    - 기계 메트릭(CPU, 지연시간, 에러율)
- 이 트렌드들을 얻기 위해 서로 특화된 데이터 파이프라인을 이용하다보면 문제가 생긴다
```
        [Oracle]  [User DB]  [활동 로그]  [메트릭]        ← N개 소스
            │  ╲    │   ╲     │    ╲       │
            │   ╲   │    ╲    │     ╲      │              각 쌍마다
            ▼    ╲  ▼     ╲   ▼      ╲     ▼              전용 파이프라인
        [Hadoop] [검색] [모니터링] [추천] [DW] [캐시]      ← M개 목적지

        필요한 파이프라인 수 = N × M  (최악의 경우 O(N²))
```

> "Connecting all of these would have lead to building custom piping between each pair of systems something like this... This clearly would take an army of people to build and would never be operable."

- O(N²) 문제의 실질적 고통은 파이프라인 개수 자체보다 다음에 있다
  - 각 파이프라인이 자체 스키마 가정, 자체 재시도 로직, 자체 장애 모드를 가짐
  - 새 시스템 하나 추가 = 기존 N개 전부와의 연결 작업
  - 한 소스의 스키마 변경 = 그에 연결된 모든 파이프라인 동시 수정
  - 소유권 불분명: 파이프라인은 양쪽 팀 중 누구의 것도 아님

## 해결방법

> The solution involves **"a central log for real-time subscription."** Each data source becomes its own log; subscribing systems read, apply changes to their stores, and advance their position.

```
   [Oracle]   [User DB]  [활동 이벤트]  [메트릭]
      │           │           │            │
      └───────────┴─────┬─────┴────────────┘
                        ▼  publish
        ╔═══════════════════════════════════╗
        ║   중앙 로그 (Kafka)                 ║
        ║   토픽별 append-only, 오프셋 부여     ║
        ╚═══════════════════════════════════╝
                        │  subscribe (각자 자기 오프셋 보유)
      ┌──────┬──────────┼──────────┬────────┐
      ▼      ▼          ▼          ▼        ▼
  [Hadoop] [검색]   [모니터링]   [추천]    [DW]

        필요한 연결 수 = N + M
```

- 원문이 정리한 이 구조의 이점 네 가지

| 이점 | 설명 |
|---|---|
| **논리적 타임스탬프 제공** | 모든 소비자가 "어디까지 봤는지"를 오프셋 정수 하나로 표현 |
| **생산자/소비자 간 비동기 버퍼** | 느린 소비자가 빠른 생산자를 막지 않음. 소비자 장애가 생산자에 전파되지 않음 |
| **소스 시스템 종류로부터의 독립** | 소비자는 원본이 Oracle인지 이벤트인지 알 필요 없음 |
| **파이프라인 수정 없이 소비자 추가** | 새 시스템은 기존 로그를 처음부터 읽으면 됨 |

- "비동기 버퍼" 항목이 특히 중요하다
  - 점대점 파이프라인에서는 다운스트림 장애가 업스트림으로 backpressure된다
  - 중앙 로그는 그 사이에 내구성 있는 버퍼를 끼워 넣어 failure isolation을 만든다

### Kafka의 탄생

> Kafka는 메시징 시스템의 개념 + 데이터베이스 로그의 원리를 결합한 것이다

```
        메시징 시스템에서 가져온 것          DB 로그에서 가져온 것
        ─────────────────────────         ──────────────────────
        · 발행/구독 모델                    · append-only 구조
        · 다중 구독자                       · 순서 보장
        · 토픽/파티션 개념                   · 디스크 영속성
        · 클라이언트 API                     · 오프셋 기반 위치 추적
                          ╲             ╱
                           ▼           ▼
                        ┌─────────────────┐
                        │      Kafka      │
                        └─────────────────┘
```

- 이 조합이 왜 새로웠는가
  - 당시 메시징 시스템(JMS, AMQP 계열)은 메시지를 소비 후 삭제했고, 브로커가 소비자별 전달 상태를 관리했다
  - Kafka는 이를 뒤집어 브로커는 로그만 유지하고, "어디까지 읽었는지"는 소비자가 관리하게 했다
  - 이 한 가지 결정에서 다음이 전부 따라 나온다
    - 브로커가 소비자 상태를 관리하지 않으므로 소비자 수에 대한 확장성이 O(1)
    - 같은 데이터를 여러 소비자가 서로 다른 속도로 읽을 수 있음
    - 재생이 가능 — 오프셋을 되감으면 과거를 다시 읽음
    - 브로커 로직이 극단적으로 단순 → 성능 최적화 여지가 큼

### 중앙 집중식 로그는 느릴수밖에 없지 않을까?

- "중앙 로그 하나에 회사의 모든 데이터를 넣는다"는 발상에 대한 즉각적 반론은 "그게 병목이 되지 않느냐"이다

#### (1) 파티셔닝: 굳이 모든 것을 Serial하게 처리할 필요가 있나?

> "Each partition is a totally ordered log, but there is no global ordering between partitions."

```
Topic: user-clicks
┌─ Partition 0 ─────────────────────┐   각 파티션은 독립된 로그
│ 0 │ 1 │ 2 │ 3 │ 4 │               │   → 독립된 서버에 배치 가능
├─ Partition 1 ─────────────────────┤   → 독립적으로 append 가능
│ 0 │ 1 │ 2 │                       │   → 조정(coordination) 불필요
├─ Partition 2 ─────────────────────┤
│ 0 │ 1 │ 2 │ 3 │ 4 │ 5 │ 6 │       │   파티션 간 순서는 정의되지 않음
└───────────────────────────────────┘
```

- 순서를 포기하는 대신 수평 확장을 얻는다
- 파티션 키 설계가 순서 보장 범위를 결정합니다
  - `user_id`로 파티셔닝 → 같은 사용자의 이벤트는 순서 보장, 사용자 간에는 보장 없음
  - `order_id`로 파티셔닝 → 주문 단위 순서 보장
  - 키 없이 라운드로빈 → 순서 보장 없음, 최대 처리량
- 문제
  - "사용자 테이블과 주문 테이블의 변경을 서로 다른 토픽으로 흘리면 두 토픽 간 순서 보장이 없다"
  - 이 때문에 CDC로 여러 테이블을 복제할 때 외래 키 제약 순서가 깨질 수 있다
  - Debezium 사용 시 흔히 부딪히는 문제이며, 해법은 (a) 관련 테이블을 같은 키로 같은 토픽에 넣거나 (b) 소비 측에서 최종 일관성을 허용하는 것이다

#### (2) 배칭 — 작은 연산을 큰 연산으로

> "group small reads and writes together into larger, high-throughput operations"

- 배칭이 적용되는 지점이 **네 군데 전부**라는 점이 중요하다

```
[클라이언트] ──①배치 전송──▶ [브로커] ──②배치 디스크 쓰기──▶ [페이지 캐시/디스크]
                                 │
                                 ├──③배치 복제──▶ [팔로워 브로커]
                                 │
                                 └──④배치 전송──▶ [컨슈머]
```

- 배칭이 효과적인 이유
  - 메시지 하나당 고정 비용(시스템 콜, 네트워크 왕복, 디스크 seek, 프로토콜 헤더)이 페이로드 크기와 무관하게 발생하기 때문이다
  - 1KB 메시지 1000개를 개별 전송하면 고정 비용 1000회, 1MB로 묶으면 1회이다
- 트레이드오프
  - 배칭은 처리량을 지연시간과 맞바꾼다

#### (3) 순차 I/O — 로그 구조의 본질적 이점

> "A log, like a filesystem, is easy to optimize for linear read and write patterns."

- append-only라는 제약이 write에 매우 유리한 패턴이기 때문이다

| 접근 패턴 | HDD (2013 기준) | NVMe SSD (2026 기준) |
|---|---|---|
| 랜덤 I/O | ~100 IOPS, 실질 수 MB/s | ~1M IOPS, 수 GB/s |
| 순차 I/O | 100~200 MB/s | 3~14 GB/s |
| 격차 | **수백~수천 배** | **수 배** (여전히 유의미) |

- 여기서 나오는 유명한 결과
  - "디스크가 느리다"는 통념은 랜덤 접근에만 참이다
  - 순차 접근 시 디스크는 네트워크보다 빠를 수 있다
  - 더 중요한 건 OS 페이지 캐시의 활용이다
  - Kafka는 자체 캐시를 두지 않고 OS 페이지 캐시에 의존한다
    - JVM 힙에 데이터를 들고 있지 않음 → GC 압력 없음
    - 브로커 프로세스 재시작 시에도 캐시가 유지됨
    - 최신 데이터를 읽는 소비자(대부분의 경우)는 디스크를 전혀 건드리지 않고 페이지 캐시에서 바로 나감
